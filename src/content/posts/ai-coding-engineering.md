# 从 Vibe Coding 到可靠交付：Anthropic、OpenAI 与国内大厂的 AI Coding 工程实践

_——关于上下文工程、Spec 驱动开发、Agent Harness、测试验证与人机协作的系统整理_

**资料整理时间：2026 年 11 月**

## 一、引言：AI Coding 的核心问题已经改变

随着 Claude Code、OpenAI Codex、TRAE 等工具的发展，AI 编程逐渐从代码补全、函数生成，发展为能够自主阅读代码仓库、调用工具、修改文件、执行测试的 Coding Agent。

但模型能够生成代码，并不意味着它能够可靠地完成软件工程任务。

传统 Vibe Coding 的典型过程是：

> 描述需求 → AI 生成代码 → 运行发现问题 → 继续让 AI 修改 → 直到看起来可以使用。

这种方式适合原型验证，但在复杂项目中容易出现几个问题：

- **需求理解偏差**：AI 实现了表面功能，却遗漏业务规则。
- **缺乏设计约束**：数据模型、模块边界与技术方案随着生成过程不断变化。
- **无法有效验证**：程序能够启动，但核心业务逻辑不一定正确。
- **上下文丢失**：长任务中，AI 忘记此前的重要决策。
- **技术债积累**：生成速度提高，但代码重复、耦合与架构不一致的问题可能更严重。

这些问题促使 AI Coding 从 Prompt Engineering（提示词工程）向 Context Engineering（上下文工程），再向 Harness Engineering（Agent 运行与验证环境工程）发展。

本文将从 Anthropic、OpenAI 及国内互联网企业的公开实践中，整理出一套可迁移到真实开发项目中的方法。

## 二、Anthropic：让 AI 理解任务，并拥有验证结果的能力

### 2.1 从 Explore → Plan → Code → Commit 开始

Anthropic 在 2025 年发布的 _Claude Code: Best practices for agentic coding_ 中，总结了一个经典工作流：

**Explore → Plan → Code → Commit**

#### Explore：先理解代码与需求

让 Agent 阅读相关代码、定位功能入口、了解现有架构，不要立即修改。

对于已有项目，重点是识别：

- 哪些模块负责当前业务？
- 有哪些现成函数与组件可以复用？
- 数据如何流转？
- 修改可能影响哪些已有功能？

其目的不是让 Agent 阅读整个仓库，而是以任务为中心获取必要上下文。

#### Plan：先确定方案

对于具有一定复杂度的任务，先明确实现方式。

一个有效的 Plan 应该回答：

1. 需要修改哪些模块？
2. 数据结构和接口如何设计？
3. 核心逻辑和重要约束是什么？
4. 怎样验证实现正确？

计划不必过度详细。小任务可以只有几句话，大型重构则值得使用独立的设计文档。

#### Code：按照计划实现

Agent 根据方案逐步修改代码，并在过程中进行必要的检查。

工程师的作用不是逐行指挥，而是关注设计方向、业务规则以及重要风险。

#### Commit：形成可回退的阶段成果

每完成一个相对独立的工作单元，就可以检查 Diff、执行验证并提交 Git。

这样既可以控制变更范围，也方便出现问题时回退。

需要注意，这个四阶段流程来自 Anthropic 的早期文章。官方已将持续维护的最佳实践迁移到 Claude Code 文档，因此它应被看作一种通用方法，而不是所有任务都必须执行的固定模板。

### 2.2 2026 年的新重点：信息、检查与强制约束

Anthropic 更新后的官方最佳实践将重点归纳为三个方向。

**第一，告诉 Agent 它无法自己获取的信息。**

例如：

- 团队未写入代码的业务约定。
- 不允许修改的敏感目录。
- 特定模块的历史设计原因。
- 项目独有的启动、测试和部署方法。

这些信息可以存放在 `CLAUDE.md` 中。

但文件应该简短。Agent 能从代码推导出的内容，不必重复写成规则。

**第二，给 Agent 一个可执行的检查。**

比起告诉 Agent“确保代码正确”，更有用的是提供：

- 单元测试命令。
- TypeScript 类型检查。
- 构建与 Lint。
- 浏览器自动化测试。
- UI 截图及设计稿对比。
- 业务验收脚本。

这样 Agent 才能形成：

**修改 → 执行检查 → 读取失败结果 → 修复 → 再次验证**

的闭环。

**第三，把绝对不能违反的要求交给确定性机制。**

提示词和规则文件并不能保证模型始终遵守要求。

例如，“禁止访问生产数据库”不能只写在 Prompt 里，而应该使用权限控制和沙箱；“类型检查必须通过”也可以通过 CI 或 Hook 强制执行。

这里存在一个重要的工程分层：

| 机制        | 适合解决的问题               |
| ----------- | ---------------------------- |
| Prompt      | 当前任务目标与约束           |
| `CLAUDE.md` | 项目级长期约定               |
| Skills      | 特定场景的可复用操作流程     |
| Hooks       | 工具调用与执行过程的强制控制 |
| Tests / CI  | 实现正确性的确定性验证       |
| Sandbox     | 文件、命令和环境的访问边界   |

核心思想是：**不要把所有工程约束都寄托在模型的自觉性上。**

### 2.3 长任务：通过外部状态维持连续性

在 _Effective harnesses for long-running agents_ 中，Anthropic 研究了 Agent 跨多个上下文窗口完成大型应用的问题。

早期 Agent 经常出现两类失败：

- 试图一次完成所有功能，结果在上下文耗尽时留下半成品。
- 已经实现部分功能，却误以为整个项目完成了。

他们采用了初始化 Agent 与编码 Agent 的分工。

初始化阶段建立功能清单、启动脚本和进度记录；后续编码阶段每次完成一部分功能，并在 Git 和进度文件中保存状态。

2026 年的后续研究又尝试了 Planner、Generator、Evaluator 的结构：

- Planner 负责定义和覆盖任务范围。
- Generator 负责具体实现。
- Evaluator 根据标准独立检查结果。

值得注意的是，Anthropic 后来也发现：随着模型能力提高，过多的任务拆分、上下文重置和评估环节可能变成额外负担。

因此，更合理的原则不是永远使用多 Agent，而是：

**只在任务超出当前模型可靠处理能力时增加额外的工程脚手架。**

### 2.4 我们能学到什么？

Anthropic 的实践可以归纳为：

> 提供必要信息，明确完成标准，建立反馈机制，并把真正重要的约束交给程序执行。

对个人开发者而言，最值得先做的事情并不是编写一套庞大的 Skills 系统，而是：

1. 写好项目说明。
2. 先确认重要设计。
3. 给 AI 配置真实可运行的检查。
4. 让 AI 根据检查结果不断迭代。

## 三、OpenAI：从使用 Coding Agent 到 Harness Engineering

与 Anthropic 类似，OpenAI 也强调规划、上下文和测试，但其公开的 Harness Engineering 实验进一步提出了一个问题：

**如果大量代码都由 AI 生成，那么工程师应该怎样重新设计整个软件开发环境？**

### 3.1 日常开发：把 Prompt 写得像 GitHub Issue

在 2026 年 1 月的 _How OpenAI uses Codex_ 中，OpenAI 总结了内部团队利用 Codex 进行代码理解、重构、性能优化、测试和功能开发的经验。

其中一项建议是：对较大的改动，先讨论实现计划，再进入编码阶段。

同时，Prompt 应尽量包含类似 GitHub Issue 的信息：

- 需求背景。
- 需要修改的模块或文件。
- 期望行为。
- 现有代码参考。
- 约束与验收条件。

例如，与其说：

> 帮我实现预约功能。

不如说：

> 在现有服务中增加预约接口，复用当前的数据访问层，预约不能产生时间冲突。先确认数据模型和冲突判断方式，再实现并验证正常及冲突场景。

这种 Prompt 的价值不是字数更多，而是减少对关键需求的猜测。

OpenAI 同样建议通过 `AGENTS.md` 维护仓库约定，为 Agent 提供跨任务的持久上下文。

### 3.2 Harness Engineering：让项目环境适合 Agent 工作

2026 年 2 月，OpenAI 发布了 _Harness engineering: leveraging Codex in an agent-first world_。

文章介绍了一个内部软件工程实验：一个最初由三名工程师推动的团队，在约五个月内通过 Codex 完成了约 1500 个 PR，建立了约百万行代码规模的内部产品。

按照该团队的实验规则，仓库代码全部由 Codex 生成，包括测试、CI、工具与文档。

这些是特定实验环境中的成果，不能直接推导为普通团队也能获得相同效率。

真正值得学习的是他们对工程瓶颈的重新认识。

**过去的瓶颈往往是代码写得不够快；当 Agent 可以高频生成代码后，瓶颈开始转向环境、验证、评审和架构一致性。**

因此，工程师的工作逐步转向：

- 将任务表达为清晰、可验证的目标。
- 建设 Agent 能够理解的项目环境。
- 定义架构与依赖约束。
- 提供日志、指标、测试等反馈。
- 处理 Agent 无法独立解决的判断问题。

### 3.3 给 Agent 一张地图，而不是一本巨大的说明书

OpenAI 在实践中发现，把大量内容全部写进一个 `AGENTS.md` 并不是好办法。

过长的规则会占用上下文，关键约束也容易被淹没。

因此，他们将项目仓库作为知识的主要载体，使用简洁的入口文档引导 Agent 按需读取：

- 架构说明。
- 业务模块说明。
- 设计决策。
- 数据结构。
- 测试与运行指令。

这是一种渐进式上下文提供方式。

Agent 不需要一开始就掌握整个系统，而应该知道**当前问题应该去哪里找信息**。

### 3.4 用架构约束防止代码生成失控

当 Agent 能快速生成大量代码时，架构腐化也可能更快发生。

OpenAI 的实验团队通过固定的分层结构、依赖方向检查、定制 Linter 和结构测试来约束生成结果。

例如，约定某个模块不能跨越指定的架构层直接依赖另一模块。

仅在文档中写“遵守分层架构”是不够的。

更可靠的做法是让工具在出现非法依赖时直接报告失败。

这体现了 Harness Engineering 的一个重要思想：

**与其要求 Agent 永远做对，不如设计一个能够及时发现并纠正错误的环境。**

### 3.5 让 Agent 看见真实运行效果

OpenAI 还将浏览器、日志、指标与 Trace 接入 Agent 的工作环境。

这样 Agent 不再只能根据源码推测程序是否正常，而可以：

- 启动应用。
- 操作实际页面。
- 复现问题。
- 查看运行日志。
- 检查指标。
- 验证修改后的行为。

例如，前端功能验收不应该停留在“React 代码生成成功”，而应该包含打开页面、点击按钮、提交表单以及检查错误状态。

后端服务同样需要通过真实请求、测试和运行指标验证。

### 3.6 OpenAI 还提醒我们：减少过度工程化

2026 年 9 月，OpenAI 发布了关于 Skills、`AGENTS.md` 和 Prompt 的新文章。

其中一个值得注意的变化是：随着模型能力提高，以前为了让旧模型完成任务而编写的大量复杂指令，可能已经不再必要。

例如：

- 不必要求 Agent 每次修改前阅读全部架构文档。
- 不必为每个小任务套用复杂的多阶段流程。
- 不应让不相关的 Skills 占用上下文。
- 应根据任务明确完成条件，而不是用大量抽象口号约束模型。

这与 Anthropic 后续研究的方向是一致的。

[Harness engineering: leveraging Codex in an agent-first world（2026）](https://openai.com/index/harness-engineering/)

## 四、国内大厂实践：如何让 AI Coding 进入真实研发流程

相比单个开发者使用 AI 写代码，国内企业的公开实践更值得关注的是团队协作、业务复杂度和质量管理。

### 4.1 美团：统一规范，否则 AI 会加速技术债积累

美团技术团队在 2026 年 5 月分享了一项约 31 万行代码规模的业务系统重构实践。

根据文章，该团队超过 90% 的代码由 AI 辅助生成，但代码生成效率的提高，并没有自动解决软件架构问题。

随着业务规模增加，缺少统一规范的代码出现了模块职责混乱、业务模型不一致与耦合度高等问题。

团队最终采用了三个重要方法。

**方法一：先让人达成一致，再让 AI 遵守一致的规范。**

如果团队成员本身对分层结构和业务模型没有共识，即使编写 AI Rules，也难以得到稳定结果。

因此，第一步是明确：

- 统一的模块边界。
- 数据模型与接口契约。
- 代码组织规则。
- 禁止出现的依赖关系。

然后才把这些共识转化成 Agent 可以执行的规范。

**方法二：人先完成代表性改造，再沉淀 SOP。**

团队先由主要负责人完成复杂模块的迁移，验证方案可行，再总结出标准迁移流程，让其他成员使用 AI 批量完成类似工作。

这是一种值得借鉴的模式：

**人工打样 → 提炼规则 → Agent 执行 → 人工验收。**

它尤其适合大规模代码迁移、接口替换、依赖升级和重复性重构。

**方法三：把技术债拆分到日常开发中。**

团队没有简单地停止业务、重新开发整个系统，而是结合日常业务需求逐步改造模型和架构。

其思想是让 AI 不只增加新功能，也帮助减少历史技术债。

### 4.2 美团分布式存储：AI Review 必须有证据

美团基础技术部在 2026 年 10 月公开了分布式存储系统中的 AI Coding 经验。

这是一个非常重要的高可靠性场景：并发、一致性、持久化、故障恢复等问题，可能无法仅通过普通单元测试发现。

文章中一个典型案例是，团队对 AI 评审提出的 117 项疑似问题逐条尝试验证：

- 36 项通过失败测试得到确认。
- 3 项被测试证伪。
- 41 项需要根据源码确认。
- 37 项尚未验证。

这个案例说明，AI 给出的 Bug 判断不能直接当成事实。

更合理的流程是：

**AI 提出问题 → 构造可执行证据 → 复核实际风险 → 决定是否修复。**

例如，AI 发现可能存在竞态条件，可以进一步编写并发测试或使用 ThreadSanitizer，而不是仅凭静态分析就宣布系统有 Bug。

同样重要的是，AI 有时会不了解业务上的特定设计。

在某些存储系统中，为了保障数据正确性，主动终止进程可能是有意采用的策略。AI 如果不了解背景，可能错误地建议把它改成记录日志后继续运行。

因此，AI Review 能帮助发现问题，但关键业务语义和设计取舍仍需要工程师负责。

### 4.3 腾讯云：从需求到交付的七步闭环

腾讯云数据万象研发团队在 2026 年 3 月公开了基于 CodeBuddy 的研发实践。

其流程包含两个阶段、七个步骤：

| 阶段     | 具体步骤                   |
| -------- | -------------------------- |
| 基础设施 | 1. 建立项目知识库          |
| 基础设施 | 2. 定义工程 Rules          |
| 日常研发 | 3. 获取需求并创建分支      |
| 日常研发 | 4. 设计技术方案，生成 Spec |
| 日常研发 | 5. 根据 Spec 实现代码      |
| 日常研发 | 6. 单元测试与覆盖率检查    |
| 日常研发 | 7. AI Code Review          |

这个案例的特点是将 AI Coding 接入需求管理、版本控制与测试评审，而不只是代码编辑器。

例如：

项目知识库帮助 Agent 理解已有系统；Rules 约束代码规范；Spec 记录数据模型、接口和实施计划；测试验证实现行为；AI Review 在人工评审前进行初步检查。

原文报告了案例中 90% 的单元测试覆盖率，以及新人上手周期由两周缩短至三天的结果。应注意，这属于案例披露的数据，不应直接视为所有团队都能实现的通用收益。

对个人开发者来说，没有必要完整复制企业级七步流程，但其中的三个要点十分实用：

**需求结构化、实现遵循方案、结果经过验证。**

### 4.4 字节跳动：自然语言编程不等于放弃工程设计

在火山引擎开发者社区刊载的一次技术分享中，字节跳动技术负责人洪定坤介绍了使用 TRAE 开发实际应用的经历。

他的做法不是单纯描述一个功能，然后完全不关注 AI 怎么实现。

相反，他会用自然语言描述编码逻辑、技术方案和核心流程，再让 AI 将其转化为代码。

这揭示了一个重要区别：

**自然语言可以替代部分代码输入，但不能替代工程设计。**

工程师仍然需要判断实现方案是否合理，只是从亲自编写大量实现细节，转向更高层次的技术表达和结果验收。

字节的实践也提出了从 AI Coding 向 AI Development 扩展的方向，即覆盖文档、调试、测试、构建、部署等更多研发环节。

### 4.5 阿里云社区：从 PRD 理解到代码验收

阿里云开发者社区刊载的《AI Coding 后端开发实战》提出了一个值得借鉴的观点：

AI 可能具有很强的编码能力，但未必拥有开发者在真实项目中积累的业务上下文。

其后端开发流程强调：

1. 阅读并理解 PRD。
2. 分析现有代码，识别可复用模块与需要修改的功能。
3. 结合业务理解生成开发概要。
4. 明确方案后进行实现。
5. 检查 AI 产出，并沉淀必要的项目文档。

它的价值在于提醒开发者：不能默认模型理解业务，必须通过代码、文档、规则及人工确认补齐信息。

## 五、综合实践：建立一套适合个人开发者的 AI Coding 工作流

对以上实践进行比较，可以发现它们并不存在完全统一的固定流程，但都强调任务范围、上下文和可验证结果。

我将这些原则整理为六个阶段。

### 阶段一：需求澄清（Requirement）

**目标：明确要实现什么。**

在开始之前，至少确定：

- 核心功能。
- 业务约束。
- 输入与输出。
- 哪些功能不在本次范围内。
- 如何判断开发完成。

对于不明确的需求，可以先让 AI 提出关键问题。

这里最重要的是消除影响架构和正确性的歧义，而不是把所有可能的边界条件都讨论一遍。

### 阶段二：方案设计（Design）

**目标：决定怎么实现。**

根据任务大小，方案可以包含：

- 技术栈选择。
- 数据结构与存储方式。
- 接口设计。
- 核心业务逻辑。
- 并发与异常处理。
- 影响范围。

这一阶段建议明确一个原则：

**开始编码之前，开发者至少应该能够解释核心数据模型和关键业务规则。**

对于复杂任务，可以让 Agent 生成 `SPEC.md`；对于短时间开发任务，确认一段简洁的方案即可。

### 阶段三：任务规划（Plan）

**目标：把方案转换为可执行工作。**

例如，一个简单业务功能可以拆成：

数据模型 → 核心服务 → API → 前端交互 → 测试。

大型功能可以保存为 `plan.md`，并使用 Git 提交记录进度。

任务分解的粒度应与实际复杂度相适应。

不需要为了完成一个很小的接口，引入庞大的任务管理机制。

### 阶段四：编码实现（Implement）

**目标：按照已经确认的方案实现。**

Agent 可以自主执行常规编码操作，但应保持以下约束：

- 优先复用项目现有模式。
- 不随意扩大需求范围。
- 重大设计变更需要重新确认。
- 不进行无关重构。
- 尽量形成容易检查的代码变更。

如果前面的方案已经足够清晰，编码阶段的 Prompt 可以非常简单：

> 按刚才确认的方案开始实现。遵循项目现有规范，完成后运行相关检查。

没有必要每一轮都重复完整的设计要求。

### 阶段五：测试与验收（Verify）

**目标：证明程序符合需求，而不只是能运行。**

建议从四个层次进行验证：

| 验证层次   | 核心问题                           |
| ---------- | ---------------------------------- |
| 静态检查   | 代码能否编译，类型和规范是否正确？ |
| 单元测试   | 核心业务规则是否正确？             |
| 集成测试   | 模块之间的真实调用是否正常？       |
| 端到端验收 | 从用户角度看，功能是否真正可用？   |

尤其需要区分“测试执行成功”和“测试具有足够的验证能力”。

例如，接口全部返回 HTTP 200，并不等于预约冲突规则正确。

测试还应该覆盖：

- 正常流程。
- 输入边界。
- 异常路径。
- 状态变化。
- 并发行为（如果业务需要）。
- 历史功能回归。

对高风险业务，还需要故障注入、性能验证、安全检查和必要的人工复核。

### 阶段六：Review 与知识沉淀

**目标：确保改动符合工程要求，并减少下一次重复劳动。**

开发完成后，可以让 AI 针对 Diff 做一次独立 Review，重点关注：

- 逻辑错误。
- 安全问题。
- 业务约束遗漏。
- 兼容性风险。
- 缺失的关键测试。

随后人工检查重要结论和实际执行证据。

对于反复出现的问题，可以进一步沉淀为：

- 项目 Rules。
- 可复用的 Skills。
- 自动化测试。
- CI 检查。
- 架构约束。
- 代码库文档。

不过，只有稳定、重复出现的流程才值得封装为 Skill。临时问题往往通过修改方案或补充一条测试就能解决。

## 六、实际案例：使用 AI 实现会议室预约系统

假设面试给出如下需求：

> 实现一个会议室预约系统，有三个固定会议室，用户可以填写预约人和时间，同一个会议室的预约不能发生时间冲突。技术栈、前后端和存储方式自由选择。

如果直接把题目交给 AI 开发，可能出现一种情况：程序页面可以使用，但开发者并不清楚预约数据存在哪里、冲突是如何判断的。

按照本文整理的方法，可以采用更可靠且简洁的流程。

### 第一步：先由开发者确定核心设计

例如：

**数据模型**

`Room`：

- `id`
- `name`

`Reservation`：

- `id`
- `roomId`
- `reservedBy`
- `startTime`
- `endTime`

会议室固定为三个。

如果选择内存存储，可以使用一个集合保存全部预约，并通过房间 ID 进行筛选。

需要明确：内存方案简单，但进程重启后数据会丢失。

**冲突规则**

采用左闭右开的时间区间 `[start, end)`。

对于同一会议室，两个预约发生冲突，当且仅当：

`existing.start < new.end && new.start < existing.end`

这种规则允许前一个预约在 11:00 结束，下一个预约恰好在 11:00 开始。

还需要验证 `start < end`，并确保预约时间格式有效。

如果服务需要处理并发请求，检查冲突和插入预约必须位于同一个受保护的临界区。例如，单进程内存实现可以使用互斥锁。

### 第二步：让 AI 复核方案

第一轮 Prompt：

> 我要实现一个三个固定会议室的预约系统，采用内存存储。请先给出简洁的设计方案，包含数据模型、接口、冲突规则和测试要点。暂时不要写代码。

开发者审查方案，如果没有关键问题，就进入编码。

第二轮 Prompt：

> 方案确认，开始实现。优先完成可运行的核心功能，不增加需求之外的复杂设计。

第三轮 Prompt：

> 运行测试并验收功能，重点检查时间冲突、相邻时间段、非法输入和并发预约。列出实际执行的测试及结果，再检查是否存在明显的设计问题。

### 第三步：验收正确性

至少检查以下场景：

| 场景                                   | 预期结果     |
| -------------------------------------- | ------------ |
| 会议室 A 10:00–11:00，无已有预约       | 成功         |
| A 已有 10:00–11:00，再预约 10:30–11:30 | 冲突         |
| A 已有 10:00–11:00，再预约 11:00–12:00 | 成功         |
| A 被预约，同一时间预约 B               | 成功         |
| 开始时间晚于结束时间                   | 拒绝         |
| 同一会议室两个并发请求预约同一时段     | 最多一个成功 |

最后，开发者应该能够回答：

- 为什么采用这种数据结构？
- 为什么该冲突条件正确？
- 如何避免并发请求同时预约成功？
- 如何验证功能没有遗漏？
- 这种内存方案有什么限制？

这才是 AI Coding 中开发者需要保留的核心能力。

对于只有 15–20 分钟的面试，可以采用约 3 分钟澄清需求、3 分钟确认设计、8 分钟实现、5 分钟测试和 1 分钟说明的时间安排。

真实的大型工程则应按风险和复杂度调整流程，不需要套用面试的时间分配。

## 七、进一步思考：AI Coding 时代，什么能力变得更加重要？

以上案例反映出软件工程师的能力要求正在发生变化。

### 1. 需求理解能力

当代码生成越来越便宜，正确理解业务目标就更加重要。

工程师需要识别需求中的隐藏条件、业务边界和异常情况。

### 2. 软件设计能力

AI 可以快速实现一个给定方案，但技术选型、数据模型、架构边界以及一致性要求仍需要合理判断。

如果开发者没有独立评估方案的能力，就很难发现 AI 在关键设计上的错误。

### 3. 验证能力

未来开发者不仅要能够编写程序，更需要能够定义正确性。

这包括设计测试、构造反例、分析运行日志、理解并发错误，以及判断测试结果是否足以支持结论。

### 4. 上下文工程能力

有效使用 Agent，需要知道什么信息应该交给它、哪些信息可以从仓库获取、如何让规则与知识长期复用。

这不只是 Prompt 技巧，而是知识组织与开发环境设计能力。

### 5. 工程自动化能力

随着 Agent 能够自主调用工具，CI/CD、可观测性、自动化测试、沙箱、权限控制与开发环境标准化将变得更加重要。

它们决定了 Agent 能否从单次代码生成扩展到可靠的软件交付。

## 八、结论：AI Coding 的目标不是少写代码，而是建立可验证的开发过程

综合 Anthropic、OpenAI、美团、腾讯云、字节跳动等企业公开的工程实践，可以提炼出五条核心原则：

**第一，先明确需求，再决定实现方式。**

让 AI 生成代码之前，开发者应当理解业务规则、数据模型与关键技术约束。

**第二，给 AI 必要的上下文，而不是无限堆积提示词。**

代码仓库、设计文档、Rules 和 Skills 应按任务提供信息，避免无关内容挤占上下文。

**第三，让 Agent 有能力验证自己的工作。**

测试、构建、Lint、浏览器自动化和运行日志，都应该成为 AI Coding 工作流的一部分。

**第四，把关键工程约束变成确定性检查。**

不要仅依赖提示词保证架构、安全与质量。能由程序检查的要求，应尽可能通过工具执行。

**第五，保持人的技术判断与结果责任。**

AI 可以承担越来越多的实现工作，但工程师仍需要明确什么是正确的设计、什么样的证据足以证明正确，以及哪些风险可以接受。

因此，成熟的 AI Coding 并不是完全放弃对代码和系统的理解，而是将开发者的注意力从重复性的实现细节，转移到需求、设计、验证和系统演进上。

最值得实践的工作方式，可以概括为：

**Understand → Design → Implement → Verify → Review → Improve**

即理解需求、设计方案、完成实现、验证结果、审查改动，以及持续改善下一次开发所依赖的工程环境。

当这个闭环建立之后，AI Coding 才有可能真正从快速生成代码，发展为可靠的软件工程协作方式。
